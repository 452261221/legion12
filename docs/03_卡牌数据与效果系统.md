# 03 卡牌数据与效果系统

卡牌系统要同时满足两个目标：早期能快速实现卡牌，长期能稳定承载大量复杂效果。建议第一阶段采用“JSON 静态数据 + GDScript 效果注册表”的方案，等规则稳定后再考虑更高层 DSL。

## 数据来源

当前资料来源：

- `规则/Q&A.xlsx`
- `规则/Q&A.docx`
- `规则/S2四阵营补强卡效果表.xlsx`
- `规则/S2彼界&奥林匹斯.xlsx`
- `规则/*.pdf`

处理原则：

- 原始资料只读保留。
- 结构化卡牌数据导出到 `data/cards/`。
- 导入脚本放在 `tools/import_cards/`。
- 导入后必须通过 schema 校验。

当前最小实现口径：

- 已有统一加载入口 `CardDatabase`，当前默认读取整个 `data/cards/` 目录并聚合全部 JSON。
- 已有最小数据校验脚本 `tools/validate_card_data.gd`。
- 已有最小整理脚本 `tools/import_cards/export_merged_cards.gd`，可将目录卡池导出为一个归并快照 JSON。
- 当前代码侧已实际支持的卡牌类型为：`legion`、`artifact`、`tactic`、`counter_tactic`、`morale`、`calamity`。
- 当前校验覆盖：卡牌 id 唯一、类型合法、状态合法、数字字段可解析、effect id 唯一、effect kind 合法、已支持 action 合法。
- 当前已落地的 stack action 最小子集包括：`draw_cards`、`add_morale`、`counter_target_stack`、`destroy_target_unit`、`discard_cards`、`deal_master_damage`、`deal_legion_damage`、`mill_cards`、`return_target_unit_to_hand`、`search_deck`。
- 当前 `search_deck` 已支持最小选择分支：看牌库顶部 `N` 张后，若符合条件的候选只有 1 张则自动拿取；若候选多于 1 张，则生成待处理 choice，由玩家从候选中点选 1 张加入手牌。
- 第一批正式 Demo 卡中，`demo_recon_order` 与新增的 `demo_pathfinder_orders` 都已接通这条检索选择链路，分别服务暮纱与晨锋预组。
- 当前这条链路已可与多模式战术叠加使用；`demo_veil_doctrine` 与 `demo_sunmarch_decree` 都会先走模式选择，再在检索分支中继续生成候选选择。
- 对 `raw_imported`、`data_imported`、`effects_stubbed` 状态，允许先保留占位 action，便于导入后再逐步实现。
- 真正独立的 `data/schema/` 与 Excel 导入器仍属于后续阶段。

当前最小圣物闭环已经落地：

- `artifact` 卡可通过 `PlayCard` 从手牌打入 `artifact_zone`。
- 圣物可在 `artifact_zone` 作为主动效果来源发动 `activated` 效果。
- `get_activatable_effects()` 已会暴露 `artifact_zone` 中圣物的可发动主动效果。
- 当前客户端已接通“点击己方圣物区直接发动唯一主动效果”的最小交互；多圣物或多效果选择 UI 仍未实现。

当前最小战术闭环也已落地：

- `tactic` 卡可通过 `PlayCard` 从手牌直接施放，使用 `row = "tactic"` 的最小施放入口。
- 首版战术不进战场、不进圣物区，而是进入临时 `stack_pending` 状态，直接生成 stack item。
- 双方过优先权后，战术效果结算并自动从 `stack_pending` 进入墓地。
- 当前已支持三种最小战术目标形态：无目标、单目标单位、敌方主宰目标。
- 当前客户端已接通：
  - 无目标战术可直接从手牌施放。
  - 单目标单位战术可在选中后点击目标单位施放。
  - 主宰目标战术可在选中后点击敌方主宰施放。
- 当前最小多模式战术 UI 已实现：若同一张战术卡存在多个可施放效果，客户端会先弹出模式选择面板，再进入对应目标选择。
- 多目标战术 UI 仍未实现。

当前最小反击战术闭环也已落地：

- `counter_tactic` 可在堆叠不为空且轮到自己优先权时，从手牌通过 `PlayCard` 打出。
- 当前最小施放入口使用 `row = "counter_tactic"`，并要求显式提供 `target_stack_id`。
- `counter_tactic` 结算后会进入墓地；若其成功反制的是 `tactic` 或其他 `counter_tactic`，被反制来源也会从 `stack_pending` 正确进入墓地。
- 当前客户端已接入最小堆叠选择 UI；若可反制目标只有一个则可直接施放，若有多个则可在 `stack` 面板中点击目标项。

## EffectDefinition

字段：

```json
{
  "id": "effect_id",
  "kind": "trigger",
  "timing": "on_enter",
  "optional": true,
  "respondable": true,
  "once": {
    "scope": "turn",
    "key": "source"
  },
  "condition": "condition_handler_id",
  "cost": "cost_handler_id",
  "targeting": "targeting_handler_id",
  "handler": "effect_handler_id",
  "tags": ["draw", "search"]
}
```

字段说明：

- `kind`：rule、continuous、active、trigger、reaction。
- `timing`：on_enter、on_death、on_attack、after_attack、turn_start、turn_end 等。
- `optional`：是否“可”发动。
- `respondable`：是否进入响应窗口。
- `once`：一回合一次、一局一次、每张卡一次。
- `condition`：发动条件。
- `cost`：支付条件。
- `targeting`：目标选择。
- `handler`：结算逻辑。
- `tags`：便于测试和查询。

## 效果注册表

GDScript 注册表：

```gdscript
class_name EffectRegistry

var handlers := {}
var conditions := {}
var costs := {}
var targetings := {}

func register_handler(id: String, callable: Callable):
  handlers[id] = callable

func resolve_handler(id: String) -> Callable:
  return handlers[id]
```

每个阵营一个文件：

```text
当前仓库尚未拆出 `rules/cards/factions/` 目录。
现阶段效果实现统一收敛在 `rules/core/game_engine.gd`。
后续若效果量继续增大，再按阵营或机制拆成独立脚本。
```

## 效果函数签名

```gdscript
func effect_handler(ctx: EffectContext) -> EffectResult:
  pass
```

`EffectContext`：

```gdscript
class_name EffectContext

var state: GameState
var source_id: String
var controller: int
var targets: Array
var choices: Dictionary
var paid_costs: Array
var triggering_event: GameEvent
var engine: GameEngine
```

效果函数必须通过 `engine.actions` 修改状态。

禁止：

```gdscript
ctx.state.players[0].master_hp -= 1
```

应该：

```gdscript
ctx.engine.actions.deal_master_damage(ctx.state, 0, 1, {"source": ctx.source_id})
```

## 关键词系统

已识别关键词：

- 强攻。
- 冲锋。
- 免死。
- 必中。
- 支援。
- 挑衅。
- 隐匿。
- 震击。
- 贯穿。
- 远程。
- 进攻无损。
- 无法进攻。
- 无法支援。

关键词应优先实现为通用 modifier 或规则 hook。

### 强攻

完整文本以规则书为准，当前先设计接口：

```gdscript
keyword_strong_attack.on_combat_damage()
```

### 冲锋

登场回合即可进攻。

实现：

- 修改 `can_attack` 查询。
- 不改变 `entered_turn`。

当前最小实现口径：

- 普通军团默认不能在登场回合攻击。
- `charge` 关键词会放开这条限制。

### 免死

即将阵亡时替代承受本次致命进攻或效果。

实现：

- 注册 replacement effect。
- 触发 `WouldDie` 时检查。

### 必中

进攻时对方无法抵挡或支援，或根据完整规则执行。

实现：

- 修改进攻防守步骤可用响应。

### 挑衅

对方进攻可选择范围内目标时，必须优先选择挑衅军团。

实现：

- 目标合法性过滤器。
- 当前最小实现会同时约束：
  - 攻击目标查询只返回挑衅单位。
  - 手工声明攻击时若绕过挑衅，校验直接拒绝。

### 隐匿

主动态效果，发动后不视为军团，覆盖时无法被选为效果或进攻目标。

注意：

- 天灾机制无法被规避。
- 不视为军团不代表不在区域。

### 远程

进攻距离 +1，远程进攻无损。

实现：

- 距离查询 modifier。
- 伤害结算 modifier。

当前最小实现口径：

- 已支持 `ranged` / `ranged_attack` 关键词用于放宽攻击距离校验。
- 当前先实现“可跨排攻击单位”的距离部分。
- `远程进攻无损` 伤害修正暂未接入，仍属于后续补强项。

### 无法进攻

当前最小实现口径：

- 已支持 `cannot_attack` 关键词。
- 攻击目标查询会直接返回空。
- 手工声明攻击会被校验拒绝。

### 进攻无损

当前最小实现口径：

- 已支持 `attack_no_loss` / `no_damage_on_attack` / `ranged_no_loss` 关键词入口。
- 当前先实现“攻击者在对单位进攻时不承受反击伤害”。
- 该规则已接入单位战斗结算，但尚未扩展到更复杂的衍生战斗流程。

## 常见效果模板

### 抽牌

```gdscript
func draw_n(ctx, n):
  return ctx.engine.actions.draw_cards(ctx.state, ctx.controller, n, {"source": ctx.source_id})
```

### 查看牌库顶部并选择

流程：

1. reveal private to controller。
2. 发出 `ChoiceRequest`。
3. 玩家选择。
4. 加入手牌。
5. 其余排序返回顶部或底部。

不能一次函数直接做完，因为需要玩家输入。

### 自选顺序返回牌库

需要 `OrderCardsCommand`。

### 选择以下一项

效果定义中声明 `options`，执行时发 `ChoiceRequest`。

### 本回合费用 -1

用 modifier：

```json
{
  "type": "cost_delta",
  "value": -1,
  "duration": "until_end_of_turn",
  "filter": {
    "faction": "olympus",
    "type": "legion"
  }
}
```

### 本回合获得关键词

用 keyword modifier：

```json
{
  "type": "keyword_add",
  "keyword": "charge",
  "duration": "until_end_of_turn",
  "target": "card_instance_id"
}
```

### 阵亡时触发其他卡阵亡效果

例如“触发其阵亡时效果”：

- 不应真的让目标阵亡。
- 应创建虚拟 `TriggerItem`，其 triggering_event 类型可为 `VirtualDeathTriggerRequested`。
- 日志记录来源。

### 主宰变军团

孙悟空类效果：

1. 支付 cost。
2. 在前排生成代表主宰的军团实例，或移动主宰实例到战场并改变类型视图。
3. 保留 master identity。
4. 进攻后或回合结束返回主宰区。
5. 离场时返回主宰区。

建议使用 `card_instance.mode = "as_legion"`，不要创建完全独立 token。

## 特殊机制接口

### 神力

奥林匹斯：

- 神力卡可视为士气。
- 可消耗并翻转神力。
- 神力数量影响费用。
- 晋升需要消耗并翻转神力。

接口：

```gdscript
get_resource_units(player, "divine_power")
consume_and_flip_resource(player, "divine_power", count)
```

### 符文

彼界：

- 消耗士气获得符文。
- 消耗符文推进试炼或抽牌。
- 符文影响战术费用和试炼卡效果。

接口：

```gdscript
gain_counter(player, "rune", count)
spend_counter(player, "rune", count)
```

如果后续确认符文需要具体卡片，再改为 resource unit。

### 试炼

需要：

- 试炼进度。
- 已完成试炼数量。
- 可完成试炼数量上限。
- 已完成试炼卡携带。
- 发动试炼无法被响应。

PlayerState：

```gdscript
var trials: Dictionary = {
  "progress": 0,
  "completed": [],
  "max_completed": 1
}
```

### 晋升

晋升：

- 消耗并翻转神力。
- 叠放至同名非晋升者军团上方登场。
- 晋升登场和登场时是分段效果。
- 落穴类效果只能无效其中一个登场效果。

实现：

- `promote_card` action。
- 创建 `PromoteEntered` 事件。
- 之后再创建普通 `Entered` 事件。

### 衍生卡

要求：

- 可由主宰或效果创建。
- 可能不进牌库。
- 可能以任何形式离场都回墓地或移除。

CardDefinition 标记：

```json
{
  "type": "token",
  "is_collectible": false,
  "can_enter_deck": false
}
```

## 导入流程

### 第一步：抽取原始表格

脚本读取 Excel：

- 卡名。
- 卡效。
- 费用。
- 兵力。
- 天灾等级。
- 卡牌属性。
- 备注。

### 第二步：生成初始 JSON

每张卡生成：

- 基础字段。
- 原始文本。
- `effects` 先空。
- `status = "raw_imported"`。

### 第三步：人工拆效果

卡牌 agent 负责把文本拆成效果段。

状态变为：

- `data_imported`
- `effects_stubbed`
- `implemented`
- `tested`

### 第四步：schema 校验

检查：

- id 唯一。
- 类型合法。
- 阵营合法。
- 数字字段可解析。
- effect handler 存在。
- limit 合法。

当前最小实现已落地为：

- `CardDatabase.validate_definition_dicts()`
- `validate_card_data.gd`
- `tools/import_cards/export_merged_cards.gd`

它先承担“最小 schema 校验器”职责，后续再演进为独立 schema 文件与导入流水线。

## 卡牌实现流程

每张卡按以下顺序：

1. 建 JSON 数据。
2. 拆效果段。
3. 为每段写 handler。
4. 写至少 1 个场景测试。
5. 写 Q&A 边界测试，如果涉及。
6. 在调试客户端中手测。
7. 更新状态为 `tested`。
