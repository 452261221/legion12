# 04 测试调试与回放

这个项目必须高度依赖自动化测试。卡牌游戏的复杂度不是代码量，而是时点和例外。没有测试与回放，后期每加一张牌都可能悄悄破坏另一张牌。

## 测试目标

- 核心规则不被 UI 影响。
- 每个规则动作可单独验证。
- 每个复杂卡牌至少有场景测试。
- Q&A 中的规则解释有回归测试。
- 任意一局对战可通过 seed 和命令日志复现。
- 调试界面可以快速造局面。

回放相关当前实现：

- `tools/replay_runner/replay_io.gd`：保存、读取并校验回放 JSON 最小 schema。
- `tools/replay_runner/replay_runner.gd`：重建牌局、校验 `ruleset_id`，并逐条执行命令。
- `tools/replay_runner/validate_replay_file.gd`：命令行校验指定 replay 文件。
- `tests/unit/test_replay_io.gd`：覆盖保存/加载、逐步 hash 校验、坏 schema 拒绝、篡改 hash 检测、缺失卡池失败、`ruleset_id` 不匹配失败、最新 replay 查找。

## 测试分层

### 单元测试

验证纯动作：

- 抽牌。
- 移动卡。
- 消耗士气。
- 翻转士气。
- 添加 modifier。
- 计算兵力。
- 检查合法目标。

### 规则流程测试

验证阶段和事件：

- 开局设置。
- 回合推进。
- 结束阶段天灾 +1。
- 天灾值高于 8 时触发。
- 进入主要阶段后可出牌。
- 持续天灾替换后应解除旧限制。
- 连续光环修正应同时影响兵力查询与真实战斗结算。

### 战斗测试

验证：

- 普通进攻。
- 远程进攻。
- 支援。
- 抵挡。
- 挑衅目标限制。
- 不可被进攻。
- 同归于尽。
- 击杀时效果。

### 堆叠测试

验证：

- 主动效果入堆。
- 触发效果入堆。
- 反应效果响应。
- 后发先至。
- 效果被无效后 cost 不回滚。
- 持续效果不能被响应。

### 卡牌测试

每个实现过的复杂卡至少一个测试。

测试名建议：

```text
test_plato_searches_top_three_olympus_card
test_achilles_replaces_lethal_damage_with_divine_power
test_wukong_returns_to_master_zone_after_attack
```

### Q&A 回归测试

资料中的 Q&A 应该变成测试。

优先覆盖：

- 冒号前 cost 与冒号后效果。
- 分段效果不能被一张无效全康。
- 主宰不视为在战场。
- 置入不触发登场。
- 支援条件。
- 阵亡视为离场。
- 主宰血量变 0 立即失败。
- 天灾机制无法被规避。
- 发动试炼无法被响应。

当前已落地的最小回归入口可先放在：

```text
tests/qa/
  test_qa_cost_vs_effect.gd
```

这个入口优先承接最容易退化的规则边界，例如：

- cost 已支付但效果被响应无效后不回滚。
- 指定 stack item 被响应无效，而不是模糊“整张牌无效”。
- 标记为不可响应的 stack item 必须拒绝被响应目标选中。

## 场景测试 DSL

为了让多 agent 写测试更快，可以提供简化 DSL：

```gdscript
var s = Scenario.new()
s.load_fixture("basic_attack")
s.play_card(0, "draw-tactic")
s.expect_hand_count(0, 1)
s.attack(0, "attacker", "defender")
s.expect_in_grave("defender")
s.expect_event("CardDied")
```

DSL 底层仍然提交命令，不直接改状态。

## 确定性随机

所有随机都来自 `RngService`。

```gdscript
class_name RngService

var seed: int
var state: int

func shuffle(array: Array) -> Array
func next_int(max_exclusive: int) -> int
func snapshot() -> Dictionary
func restore(snapshot: Dictionary)
```

禁止直接调用 Godot 全局随机。

## 回放格式

当前实现 JSON：

```json
{
  "version": 1,
  "ruleset_id": "l12-s2-dev",
  "seed": 12345,
  "initial_decks": [
    ["dev_legion_alpha", "dev_legion_alpha"],
    ["dev_legion_beta", "dev_legion_beta"]
  ],
  "winner": -1,
  "loss_reason": "",
  "commands": [
    {
      "index": 1,
      "command_id": "cmd_1",
      "player_id": 0,
      "type": "PlayCard",
      "phase_before": "main",
      "phase_after": "main",
      "payload": {"card_id": "c_001", "row": "front", "col": 0},
      "client_time": 1710000000,
      "source": "local",
      "state_hash_before": "before_hash",
      "state_hash_after": "after_hash",
      "ok": true
    }
  ]
}
```

回放时：

1. 用同一 seed 初始化。
2. 加载相同卡组。
3. 逐条命令执行。
4. 每步对比 `state_hash_before` 与 `state_hash_after`。
5. 若 replay 文件缺关键字段或字段类型错误，应先以 `INVALID_REPLAY_SCHEMA` 失败。
6. 若 replay 的 `ruleset_id` 与当前引擎不一致，应以 `REPLAY_RULESET_MISMATCH` 失败。

若 hash 不一致，回放器应立即失败并返回首条分歧命令，避免“结果看起来还能跑”却已经偏离原局面。

## 状态 Hash

每条命令后生成状态 hash，便于找首次分歧。

```gdscript
state_hash = StateHasher.hash_public_and_private_state(state)
```

hash 前要排序字典 key，避免非确定性。

## 调试命令

调试命令必须统一走规则引擎。

当前已落地的 `DebugCommand` action：

```text
draw_cards
add_morale
set_master_hp
set_calamity_value
reveal_calamity
```

当前客户端侧栏已暴露的最小调试按钮：

```text
当前抽1
当前加士气
P1血=10
P2血=10
天灾=9
翻天灾
```

对应单测现已覆盖：

- `draw_cards`
- `add_morale`
- `set_master_hp`
- 非法 action / 非法 player / 非法 count / 非法 hp / 非法天灾值 / 未知天灾

调试命令记录到日志，但标记：

```json
{"debug": true}
```

建议面板 Tab：

- State：完整状态树。
- Commands：命令日志。
- Events：事件日志。

- Cheats：造局按钮。

## 自动校验

每个测试和调试命令后运行：

```gdscript
StateValidator.validate(state)
```

严重错误直接 fail：

- 同一张牌出现在两个区域。
- 区域引用不存在的实例。
- 战场格子重复占用。
- 主宰血量为负但没有胜负结果。
- 堆叠引用不存在效果。

警告：

- 手牌超过上限。
- 卡牌缺图。
- 未实现效果被触发。

## 未实现效果策略

早期有大量卡牌未实现。不要静默忽略。

每个未实现效果应该：

- 创建 `UnimplementedEffectTriggered` 事件。
- 在 UI 调试面板中显示。
- 测试中可断言没有未实现效果。

## 验收标准

规则核心阶段验收：

- 全部单元测试通过。
- 至少 20 个基础场景测试。
- 至少 10 个 Q&A 回归测试。
- 回放能复现同一局。
- 状态 validator 无错误。

客户端阶段验收：

- 可完成 10 回合本地对战操作。
- 每个区域可视化正确。
- 出牌、进攻、结算有基础动画。
- 调试面板可造局。
- 保存回放并重放成功。
