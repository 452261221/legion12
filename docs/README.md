# 十二军团项目技术文档总览

本文档集定义《十二军团》桌面卡牌对战游戏的长期技术方案。当前目标是先完成单机调试版对战客户端：双方均由同一名玩家操作，完整搭建牌桌、区域、回合流程、抽牌、出牌、进攻、天灾、响应、结算、日志与回放。联机、AI、主界面、房间、历史、构筑等功能放在后续阶段，但架构从第一天就要能承载这些能力。

当前客户端方向：Godot 4.6.1 桌面端。

## 核心原则

1. 规则核心必须独立于 Godot UI。
   UI 可以请求操作、展示结果和播放动画，但不能直接改血量、移动牌、结算效果。

2. 所有玩家行为都必须转化为命令。
   例如 `PlayCardCommand`、`DeclareAttackCommand`、`ChooseOptionCommand`、`PassPriorityCommand`。命令经过合法性检查后产生事件与状态变更。

3. 所有状态变更都必须可追踪。
   抽牌、弃牌、支付费用、进入战场、阵亡、进入墓地、天灾翻开、响应被无效，都要进入日志。

4. 随机必须可复现。
   洗牌、随机抽取、随机天灾都必须来自带 seed 的随机源。任何 bug 都应该能通过回放日志复现。

5. 卡牌效果要建立在原子动作之上。
   卡牌不能随意改状态，只能调用规则核心提供的动作，例如 `draw_cards`、`move_card`、`deal_damage`、`apply_modifier`、`start_attack`。

6. 分段效果要尊重时点。
   资料中 Q&A 明确，类似“冒号前 cost，冒号后效果”和“分段效果不能被一张绝对防御全部无效”的规则必须进入底层模型。

7. 多 agent 开发必须靠接口协作。
   规则 agent、UI agent、卡牌 agent、测试 agent 应该修改不同目录，通过公开 API 集成，避免互相覆盖。

说明：

- 自动导出的结构化数据放在 `data/`，原始资料和可运行数据要分开。

## 第一阶段可交付物

第一阶段不追求全卡牌完整效果，追求“对战底盘正确”。

必须完成：

- 双方主宰、血量、手牌、牌库、墓地、士气牌库、士气区、圣物区、前排、后排、消耗区、天灾牌区。
- 回合阶段流转：触发天灾、重置、抽牌、士气、主要、结束。
- 基础出牌：军团、战术、反击战术、圣物、主城或特殊卡位的占位能力。
- 基础进攻：选择攻击者、选择目标、进攻距离、抵挡、支援、伤害、兵力损耗、阵亡、墓地。
- 基础效果系统：主动、触发、反应、持续、规则效果。
- 堆叠与响应：可进入堆叠的效果能被响应；持续/规则效果不进入堆叠。
- 调试面板：抽指定牌、设置士气、设置天灾、强制触发事件、查看日志。
- 回放日志：保存命令序列和随机 seed，能重跑到同一结果。

暂缓：

- 联机。
- AI。
- 完整主菜单。
- 牌库构筑器的美术和完整体验。
- 所有卡牌逐张实现。
- 商店、账号、排行榜。

## 技术选择

| 模块 | 推荐方案 | 原因 |
| --- | --- | --- |
| 客户端 | Godot 4.6.1 | 桌面打包、动画、UI、资源管理、调试便利 |
| 规则语言 | GDScript | 与 Godot 集成简单，多 agent 容易读写 |
| 测试 | 自定义 headless 脚本入口 | 与当前仓库一致，便于直接跑 bootstrap、unit tests、replay 校验 |
| 数据格式 | JSON | 易导入、易 diff、易由工具生成 |
| 回放 | JSONL 或 JSON | 每一步命令和事件可审计 |
| 卡牌效果 | GDScript 注册表 | 早期比自研 DSL 更快，后期可引入 DSL |

## 关键风险

- 规则时点复杂，尤其是响应、堆叠、触发式效果、替代承受、阵亡与离场。
- 卡牌文本中存在“置入”和“登场”的区别，不能粗暴等价。
- 主宰、圣物、军团、战术的所在区域不同，不能都当作战场实体。
- 反击战术可覆盖放置，军团不能被替换，且控制者/所有者规则影响可放置位置。
- 天灾机制无法被规避，某些隐匿或不视为军团的效果也不能逃避天灾规则。
- 神力、符文、试炼、晋升、衍生卡、主宰变军团是后续高风险机制，需要底层提前留接口。
